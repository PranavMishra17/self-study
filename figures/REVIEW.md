# Figure review

Raised by the reviewers who wrote the figure notes (2026-09-26), for the figure pass.
Clear errors were fixed at the time: the Alaap autograd formulas (W.grad is x.T @ g),
the async flag on the guide's idempotency diagram, and the collapsed ids in the chain-rule
figure. What is left are mostly omissions: a failure path not drawn, a claim in the caption
the drawing does not show. Keys: plain names are figures in figures.js, sd: the system design
guide, al: the Alaap page.

- **al:sourcefilter**: No edge connects tilt and f0 directly, even though the caption's central point is that spectral_tilt correlates strongly with f0 (r = +0.918) rather than measuring an independent property. A reader following only the arrows would see three parallel, apparently independent measurements branching off speech, with no hint that two of them are entangled.
- **al:layer**: relu feeds both drop and sm directly (relu>drop and relu>sm), as if they were parallel alternatives rather than a sequential stack. In a real network dropout normally sits between a layer and the next one in sequence (relu -> drop -> sm); as drawn here, dropout looks like a side branch that only leads to eval() and never actually reaches the output softmax, which could be read as dropout being skipped entirely on the path that matters.
- **al:conv1d**: BatchNorm is drawn as a branch off c2 running in parallel with pooling, rather than in sequence before it. In a typical ECAPA-TDNN block, normalisation happens before pooling summarises the sequence; as drawn, a reader could conclude pooling operates on the raw convolution output while normalisation is a separate, unrelated side path.
- **al:xvector**: The caption's central claim — that the embedding inherits whatever training made it ignore, namely channel and recording quality, which is why it can judge identity but never quality — has no corresponding node or edge. A reader following only the diagram's arrows would see how the embedding is produced and compared, but nothing showing why it is structurally blind to audio quality.
- **al:embed**: The edge audio>tok points at the text tokenizer node, which could be read as audio literally being routed through the BPE tokenizer. Audio is tokenized by a completely different mechanism, a neural codec, not by BPE; the edge means 'the same conceptual role', not a shared pipeline stage, and a dedicated audio-tokenizer node would make that clearer.
- **al:ttslm**: The caption claims forty voices cost the same language-model time as one, which only holds if content-token generation is speaker-independent and just the decoder varies per voice. But the diagram draws spk>lm, meaning the speaker vector also conditions the transformer's generation — if that's literally true, changing the voice would require re-running the transformer, contradicting the claimed reuse. The diagram doesn't distinguish 'speaker vector nudges generation' from 'speaker vector only matters at decode time.'
- **al:mdn**: The plain-regressor node (reg) has no edge to or from anything else in the diagram, so a reader can't see it takes the same description embedding as input. It should connect from e the same way m does, to show it is an alternative head on the same input rather than an unrelated, free-floating box.
- **al:arch-ctx**: The edges only connect each input and output to the grouping box, not to the specific inner component it actually reaches (description to the mapper, script and direction to the renderer, gate/watermark output to audio-per-line and manifest). This keeps the diagram simple but the arrows alone don't show, for example, that per-line direction never touches the identity store.
- **al:arch-tower**: The edge id box>description-text represents the dashed drift-check feedback loop (audio's re-extracted vector compared back against the description), but it is modelled as coming from the tower-B grouping box in general rather than specifically from the audio node. As drawn, the feedback loop looks like it could originate anywhere inside tower B rather than from the rendered audio specifically.
- **al:arch-mint**: The grouping box's internal gates (uniqueness, render-a-probe, drift, consistency, CER) have no edges between them, so the diagram doesn't show that render-a-probe is a prerequisite the other three measurement gates (drift, consistency, CER) actually depend on — without a rendered probe there is nothing for those three to measure. As drawn, all five look like independent, parallel checks.
- **al:arch-render**: The Direction-channel diagram describes rate as acting on the waveform via retime(), not inside the frozen TTS call, but this diagram draws a single direction>frozen-tts edge with no separate edge to retime(). A reader relying only on this diagram would conclude the frozen model consumes all of direction, both emotion and rate, directly, rather than emotion going in at render time and rate being applied afterward by the phase vocoder.
- **al:arch-gates**: The three arrows (drift to CER, consistency to CER, CER to naturalness) suggest a pipeline where each gate's output feeds the next, but the gate stack is actually five independent checks that each pass or block a render on their own; none of them consumes another gate's output as input. The arrows read as data flow where the real relationship is closer to 'drawn in the same left-to-right, calibrated-then-proposed order.' Uniqueness has no arrow to or from any other gate, which is accurate since it genuinely doesn't feed the others, but that makes it inconsistent with drift and consistency being drawn as if they do feed into CER.
- **al:arch-rev**: The final edge, measure-again to measure, loops back to the same measure node used at the very start, which is accurate since it's genuinely the same function, but a reader could misread it as continuing the pipeline into a third stage rather than closing a verification loop back to the first step.
- **al:arch-axes**: This diagram has no edges at all, so nothing shows that all ten scores are computed the same way, against the same screen (within/between-speaker variance) described in the last node. A reader who starts elsewhere in the list has no arrow pointing them back to what the scores actually mean.
- **al:arch-codec**: The pipeline arrows show a clean encode-then-decode round trip, but say nothing about which codec instance produced the content tokens versus which one is asked to decode them, exactly the gap the bug callout describes. A reader who only follows the arrows would have no way to see that this mismatch is possible, since the arrows treat 'content tokens' and 'global embedding' as generic boxes rather than tying each to a specific codec instance.
- **al:arch-mods**: geometry.py has no incoming edge from service.py or any orchestration-layer module, and no other module is shown depending on it except its own outgoing edge to captions.py. As drawn, geometry.py looks unreachable from the rest of the system, which is unlikely to be true of a module doing PCA and rescaling work that mapper.py's retrieval and blending logic would need.
- **al:arch-exp**: None of the four failed-lever nodes (more-novelty, more-corpus, more-bins, more-axes) or the two grouping boxes below the wall have any edge connecting them back to 22-effective-voices or to each other, even though the figcaption frames them explicitly as four different answers to the question that node poses. The reader has to infer the connection from the figure's vertical layout and the figcaption text, not from any arrow.
- **al:arch-stages**: Track A (S0-S5) and track B (S6-S10) are drawn as two separate chains with no edge connecting them, but the figcaption states the identity-store schema is the contract between the tracks and that track B is 'supposed to start at S1', a real dependency the arrows don't show. The figcaption also flags a genuine naming collision: the numbered experiments/S6...S10 directories on disk are unrelated Indic experiments, not the same S6-S10 as this platform track; the diagram's own node ids (s6-inference-service, and so on) don't carry that warning, so matching ids to a file listing could easily conflate the two.
- **zenmlStack**: The Stack node's only arrow reaches step: evaluate. The caption says the stack decides where the whole pipeline runs, but the drawing only shows it connected to the last step, which could read as the stack governing evaluation alone rather than every step.
- **kitaruOrder**: The candidate-set footnotes under each column (completed AND failed vs. completed only) are themselves one of the two defects the source calls out by inspection, not just a note: the same cache key can resolve to a recorded failure under baseline scope and silently skip it under agent scope. That is inconsistency, not a documented design decision, and is worth stating as a bug rather than leaving as small print.
- **attention**: The original figure drew Q, K and V as three boxes but only ever connected Q and K to a score and a softmax; V was drawn and never used, and the figure stopped at softmax without showing the output attention actually produces. Fixed by adding a scale node for the ÷√dₖ step and an output node that combines softmax's weights with V.
- **eigen**: The original figure drew each vector's arrow twice — once as a plain path, once again via S.arrow — doubling the stroke for no visual reason. Cleaned up to a single arrow per vector in the redraw.
- **overfit**: The original validation curve used tone "mark", which has no corresponding class in figures.css (only sys, math, alaap, req, iv, now, flat exist) — the curve had no stroke colour and rendered invisibly. Fixed by using tone "req" (dashed) so training and validation are visually distinct.
- **sd:notebooklm:notebooklm-high-level-design**: No edge shows blob storage telling the notebook service that a presigned upload finished; nb>queue implies the notebook service already knows the source is ready, but nothing in the diagram signals when the raw upload actually completes.
- **sd:prior-auth:prior-authorization-validator-high-level**: No edge connects docs (document processing) to evaluator; the workflow orchestrates both separately, so the diagram doesn't show how processed documents actually reach the criterion evaluator.
- **sd:email-agent:email-and-calendar-agent-high-level-desi**: No edge shows what happens when the gate blocks an action outright rather than requiring confirmation or clarification; every outgoing edge from gate (notify, trace, outbox) is a path where the action proceeds in some form or is only logged.
- **sd:coding-agent:cloud-coding-agent-high-level-design**: No edge shows a task being marked complete once the PR opens; completion presumably rides on the same events stream as ordinary progress updates, but the diagram doesn't distinguish the two.
- **sd:ticketmaster:ticketmaster-high-level-design**: No path shows seat availability reaching the CDN-cached event pages; a cached page could keep showing a seat as available after it has been held or sold, until the page's own cache TTL expires.
- **sd:alfred:background-pipeline-dana-mail-in-actions**: No edge connects draft (where the reply text is written) to user or send; pend>draft shows a draft being written and user>send shows the user approving one, but nothing in between shows how the drafted reply actually reaches the user for review.
- **sd:alfred:one-chat-turn-sms-shown-web-and-mcp-ente**: turn>trace is drawn as one edge but stands for two separate events, opening the trace at the start of the turn and closing it at the end, which the single arrow doesn't distinguish.
- **sd:alfred:alfred-high-level-design**: No edge from follow (the follow-up family) to notify; briefs has an edge to notify showing how a brief reaches the user, but follow-ups have no equivalent path shown.
- **sd:alfred:what-one-tool-call-passes-through**: The diagram draws one path from the capability gate through preview and confirm for every call, regardless of whether it is a read, write, or bulk operation; presumably only some calls actually pause for user confirmation, but the diagram doesn't branch to show that.
- **sd:kitaru:kitaru-high-level-design**: No edge shows an evaluator's score being written back to Postgres; plug is only ever spawned by the worker, with no path back to persist what an evaluator actually found.
- **sd:scaling-reads:read-path-progression**: No routing rule is shown for a read right after that same client's own write; app>primary and app>replicas both exist with nothing distinguishing the read-your-writes case from an ordinary read that can tolerate replica lag.
- **sd:denormalize**: The insert and the increment are two separate writes with nothing shown to keep them atomic; a crash between them leaves the precomputed count wrong until something reconciles it.
- **sd:replicas**: No path lets a reader see its own very recent write; every read shown goes to a replica that may still be behind the primary, the read-your-writes problem this diagram doesn't address.
- **sd:invalidation**: No safeguard is shown against a read that repopulates the cache with the stale value right after, or during, this eviction, a known race in cache invalidation.
- **sd:hot-keys**: No edge shows how copy A and copy B are kept in sync when the underlying value changes; only the read-side random pick is drawn.
- **sd:scaling-writes:write-path-under-load**: s3 is described as salted, but the diagram draws one arrow into it for key C, the same as the unsalted shards; the salting only shows up in the node's own label, not in the edge structure the way the dedicated hot-partition diagram draws it explicitly.
- **sd:sharding**: This router uses a plain hash(key), not consistent hashing; adding or removing a shard here would remap nearly every key, unlike the consistent-hashing technique described elsewhere in this guide.
- **sd:batching**: Nothing is shown for what happens to buffered writes if the process crashes before the ten-second flush; the buffer here is in-memory only.
- **sd:real-time:push-path**: Nothing reads from the connection registry; delivery in this diagram happens by topic through pubsub>conn, not by looking up a specific user's server in the registry, so the registry's only edge (conn>registry, a write) has no consumer.
- **sd:fanout-mode**: The title promises three modes (write, read, or hybrid) but the diagram only draws the two pure cases; there is no node or edge showing a hybrid strategy (e.g. fan out to most followers but pull for a few oversized ones, or cap fan-out size).
- **sd:contention:two-actors-one-resource**: The diagram draws all three strategies (lock, direct conditional write, queue) branching off the same service as if they run together; in practice a system picks one approach for a given resource, not all three for the same request. It reads as a menu, not a trace, and nothing marks it as such.
- **sd:pessimistic**: Shows B blocking but not what bounds the wait — no lock timeout is depicted, so a stuck or slow transaction A would hold B, and every other waiter, indefinitely.
- **sd:distributed-lock**: The numbered edges (1 lease expires, 2 old write, 3 new write) show both writes reaching the database, but nothing depicts the database actually applying the `token >= 6` check and rejecting the stale one — the fencing token's entire purpose is left implicit rather than shown as a step.
- **sd:reservation**: The two outcome edges (paid → confirmed, and expired → released) both use the id `hold>seat` with no distinguishing suffix (e.g. `hold>seat#2`), so they collapse into one edge and can't be walked or annotated as the two separate, mutually exclusive outcomes they represent.
- **sd:cross-service**: The title contrasts two-phase commit versus sagas, but the diagram only draws the saga side (hold, charge, compensate) — there's no coordinator, prepare phase, or vote step to represent the two-phase-commit alternative it's supposedly being compared against.
- **sd:multi-step:orchestrated-process-with-compensation**: The engine>s1, engine>s2 and engine>s3 edges are drawn as if all three always fire, but in the failure trace shown, s3 never runs — the diagram doesn't visually distinguish the 'legal path if nothing fails' edges from what actually happened in this specific trace (s2 fails, then compensation, not s3).
- **sd:saga**: Step 2's own effect (the charge) is never explicitly undone in this trace, only step 1's reservation — since step 3 is what actually failed, a real saga would also need a compensation for step 2 (e.g. a refund), but there is no `comp>s2` edge for it.
- **sd:state-machine**: `blocked` is drawn as a state alongside `proposed` and `pending_confirm`, but conceptually it reads more like a rejection response than a state a record settles into — it isn't clear from the diagram whether a blocked record is meant to sit in a real `blocked` state or simply stay in `proposed` with the transition refused.
- **sd:outbox**: There is no edge or node showing the outbox row being marked published (or deleted) after `relay>broker` succeeds. Without that step it isn't clear what stops the relay from re-polling and re-publishing the same row, and the diagram doesn't hint that downstream consumers need their own idempotency handling for the resulting duplicates.
- **sd:retries-dlq**: The diagram treats every failure the same, routing it into the same backoff-then-retry path. A transient failure (a timeout, a 503) is worth retrying; a deterministic one (malformed input, a 4xx) will fail identically every time and should go straight to the DLQ instead of spending a retry budget on it. That distinction isn't represented.
- **sd:leases**: Nothing shows what happens if worker A wasn't actually dead and finishes its own attempt after B has already claimed the job. A real system needs a fencing token or an idempotent effect to stop both workers' results from being applied; that safeguard is only implicit here, not drawn.
- **sd:priority-cancel**: The diagram shows strict priority — drain high, then low — with no starvation guard. If high-priority jobs arrive continuously, the low queue is never served; a real system usually needs some fairness mechanism (weighted or aging priority) to bound how long low-priority work waits, and that isn't represented.
- **sd:metadata-split**: The `storage>meta` edge implies object storage writes directly to the application's metadata database, but object storage systems don't do that. In practice this transition is driven by a storage-event notification consumed by a separate processor — shown as the events/proc nodes in the large-blobs overview diagram — not by a direct edge from storage to metadata.
- **sd:storage-events**: Delivery is at-least-once (the guide's own tradeoff for this technique), but the diagram shows no dedupe or idempotency check on 'proc' — nothing stops the same object being scanned or thumbnailed twice.
- **sd:cdn-signed**: Revocation is only as fast as the signed URL's own expiry (the guide's own tradeoff) — there's no way shown here to cut off access to an already-issued link before it expires on its own.
- **sd:hashing**: Cross-user dedupe can leak that specific content already exists (a hash hit is itself information, even without exposing the content) — the guide names this as a real cost of the technique, and the diagram doesn't surface it.
- **sd:scan**: Fine for a small set, but the diagram doesn't say where it breaks: this is the guide's own baseline, and it degrades badly once the dataset reaches hundreds of thousands of items.
- **sd:geohash**: Geohash cells are uneven in physical size near the poles, and the edge/neighbor check shown here is the direct cost of that unevenness — worth naming, since it's the technique's main tradeoff.
- **sd:cells**: Still needs an exact-distance filter after this covering step, the same second pass shown in the geo pattern's own overview diagram — this diagram stops at 'covers' and doesn't draw that filter.
- **sd:builtin**: Trades a purpose-built geo service for simplicity, which means this inherits whatever scaling limits the underlying store already has — the diagram doesn't show that ceiling.
- **sd:reliability:failing-safely**: The gateway's label says it checks health, but no edge shows it polling service replicas for health — only the routing edge (gw>svc) is drawn.
- **sd:replication-failover**: Synchronous replication (drawn here) trades write latency for safety; the diagram doesn't show the asynchronous alternative, which is faster but can lose the last acknowledged write on failover.
- **sd:timeouts-retries**: Retries are shown as jittered, but the diagram doesn't state the precondition that makes them safe: only idempotent calls should be retried, or a false timeout on a non-idempotent call can duplicate its effect.
- **sd:circuit-breaker**: A breaker is only useful with a real fallback and thresholds tuned empirically (the guide's own tradeoff) — neither is shown; the diagram draws 'fallback' as if it were free to build.
- **sd:bulkhead**: Isolating pools means idle capacity in pool B can't be lent to pool A even when pool A genuinely needs it — the guide's own tradeoff (less efficient use of total capacity) isn't visible in the diagram.
- **sd:degradation**: The reduced answer should be visibly marked as reduced (per the guide's own tradeoff) — the final edge just says 'reduced answer' without showing that the client is told it's degraded.
- **sd:rate-limiting**: A legitimate burst is throttled the same as abuse (the guide's own tradeoff), and a distributed deployment needs shared state for the limiter to be enforced consistently across instances — neither distinction is shown.
- **sd:flags**: Old flags left in the codebase after a rollout finishes become dead code paths nobody remembers to remove — the guide's own tradeoff (flag debt) — and there's no cleanup step shown.
- **sd:monitoring**: Alerts need an owner or they become noise (the guide's own tradeoff), and there's no mechanism shown for deciding how large a gap must be before it's worth paging someone.
- **sd:multi-region**: Async replication (as labeled here) means a failover can lose whatever hadn't yet replicated to region B when region A went down — that gap isn't shown, and active-active would need its own conflict handling that also isn't shown.
- **sd:consistency:one-source-of-truth-many-copies**: The 'reader>primary: own writes' edge assumes the service already knows a given reader just wrote something; nothing in the diagram shows how that's tracked, which the read-your-writes technique itself names as needing a tracked session.
- **sd:read-your-writes**: Routing a user's reads to the primary for a window after they write adds load to the primary exactly when it's already busy handling that write (the guide's own tradeoff), and the diagram doesn't show how that window is tracked, session, cookie, or otherwise.
- **sd:quorum**: If replica 2 and replica 3 disagree, the reader has to reconcile the two answers, typically by taking the higher timestamp or version — the diagram shows both being queried but not that reconciliation step.
- **sd:cdc**: Consumers tailing the log have to handle replays and preserve ordering (the guide's own tradeoff), and a consumer that falls behind or restarts needs to resume from the right point in the log — neither is addressed here.
- **sd:event-sourcing**: Rebuilding state from a long log gets slower over time, and changing the event schema after the fact is genuinely hard (the guide's own tradeoff) — this diagram shows the happy-path replay but not snapshotting or schema evolution, the usual answers to that cost.
- **sd:search:hybrid-search**: The 'vec' node's own label says it's 'embedded on CDC', but only the 'src>inv' edge is drawn — the same CDC-driven re-embedding path into the vector index is implied but never shown.
- **sd:inverted**: This index is a separate system, only eventually consistent with the source (the guide's own tradeoff), and nothing in this diagram shows the update path that keeps it in sync; that path is the cdc technique, drawn in the search pattern's overview but not repeated here.
- **sd:pg-fts**: Weaker ranking and scaling than a dedicated search engine is the guide's own stated tradeoff for this technique; it's a 'good enough without another system' choice, not a drop-in replacement for the inverted-index technique.
- **sd:vector**: Approximate nearest-neighbor search is weak on exact terms like names and ids (the guide's own tradeoff); the diagram shows no fallback to exact or keyword matching for those cases, which is exactly why the search pattern's overview combines this with an inverted index rather than using vector search alone.
- **sd:hybrid-rerank**: The rerank step adds real latency and cost (the guide's own tradeoff); nothing in the diagram indicates that cost, which is why fusing first and only reranking a small candidate set, not everything, is the actual design decision being made here.
- **sd:topk**: The diagram doesn't show how the heap handles decay of old trends; a raw count-min sketch never forgets, so a real top-K trending feature needs a windowed or decaying variant, which isn't visible here.
- **sd:llm-cost:spend-tokens-only-where-they-matter**: Context budgeting — one of the seven llm-cost techniques, and one of the largest cost levers because it trims what's sent to the model at all — has no node in this overview, which otherwise covers routing, caching and batching but not input-side trimming.
- **sd:streaming**: Nothing shows what happens when verify rejects output the user already saw streamed — streaming and a hard verification gate are in tension, since tokens already rendered can't be unshown.
- **sd:prompt-cache**: The diagram shows caching as a pure win ('reused, free'), but prefix caches usually expire after a few minutes of inactivity and any change to the prefix — even one token — invalidates the whole cache; that fragility isn't visible here.
- **sd:routing**: Two edges leave 'small' — straight to answer, or escalate to large — but nothing shows a path for when the small model's own classification was wrong; a request it wrongly judged easy has no way back into the hard path once answered.
- **sd:early-exit**: A rule set needs maintenance and can go stale; a rule that used to be correct but no longer matches current inputs would silently fall through to the model rather than fail loudly, and that failure mode isn't shown.
- **sd:context-budget**: The diagram shows a single trim step, but not what the guard does when the relevant information turns out to be in the part it cut — a real budget guard needs a way to retrieve more on demand, not just cut once.
- **sd:batch-parallel**: 'jobs' feeds both paths from the same node, but nothing shows what decides which path a given batch of calls takes — that decision (latency need vs. cost) is the actual design choice and isn't represented as a node or edge label.
- **sd:response-cache**: A semantic hit on embedding similarity risks returning a confidently wrong answer for a question that's similar but not equivalent (same topic, different constraint); the diagram draws exact-hash and embedding hits as the same 'cache' node with no similarity threshold shown.
- **sd:grounding:generate-verify-measure**: Shadow mode and online signals — comparing a candidate change against production on real traffic — is part of the same grounding pattern group but doesn't appear here; the feedback loop shown goes straight from evals to gen, skipping the shadow-testing step that normally sits between them.
- **sd:rag**: This diagram has no verification step after generation, unlike the related grounding overview (sd:grounding:generate-verify-measure), which adds a verify stage checking citation markers against sources. Without it, RAG alone doesn't guarantee the answer stuck to the passages it was given.
- **sd:citations**: Nothing shows what happens to the rest of the answer when one claim's citation fails — does the whole answer get rejected, or just that one sentence dropped? 'Unsupported dropped' on the out node implies per-claim dropping, but that isn't drawn as a distinct path from verify.
- **sd:structured**: No path is shown for a validation failure — retry with the error fed back, fall back to a default, or reject the request. 'Valid only' reaching the consumer implies invalid output just disappears, which is an incomplete story for a guard node.
- **sd:refusal**: No verification step sits between 'gen' and 'answer', unlike sd:citations or the grounding overview — this diagram trusts the model's own judgment that evidence was found, with nothing checking that judgment before the answer ships.
- **sd:eval-gate**: A golden set that never grows becomes stale relative to real traffic; there's no path shown for a new failure case found in production getting added back into the golden set, so the gate can only catch regressions on problems it already knew about.
- **sd:shadow-online**: There's no promotion path shown for a candidate leaving shadow mode and becoming production — the diagram stops at comparison, without the decision step (what score, over what traffic volume, triggers promotion).
- **sd:agent-safety:from-proposal-to-effect**: Effect classes — sorting tool calls by read, reversible, or irreversible — is one of the six agent-safety techniques but has no dedicated node here; it's folded silently into 'policy gate', even though the policy gate's own diagram (sd:policy-gate) treats classification as a separate concern from the allow/ask decision.
- **sd:policy-gate**: The gate is described as turning 'features' into a verdict, but the diagram doesn't name what those features are (effect class, taint, scope); without that, the gate reads as a black box rather than the deterministic rule it's meant to be.
- **sd:effect-classes**: The three outgoing edges from 'classify' read as a strict partition, but many real actions are mixed — a call that reads a large amount of data and also writes a log entry, for instance — and the diagram gives no guidance for a call with effects in more than one class.
- **sd:hitl-undo**: The 30-second undo window is a specific, concrete number with nothing indicating it's illustrative rather than a fixed constant; a real system would size this window to how fast a person can notice and react to a given action, not use one number for every reversible action.
- **sd:least-privilege**: 'blocked' (Merge) is tone 'guard' while 'allowed' (Open PR) is tone 'external', which frames merge as a policy check rather than as a parallel action the token either has or doesn't have — the more accurate framing, matching how 'allowed' is drawn.
- **sd:injection**: The diagram implies taint is binary and permanent once attached at the reader, but doesn't show whether it clears or how it composes — if the planner combines a tainted field with clean data before acting, does the resulting action stay tainted? That composition rule is the hard part of this technique and isn't represented.
- **sd:budgets**: '3x same call' catches only exact repetition; it doesn't catch an agent cycling through a small set of different calls without making progress, which a real loop guard usually needs a broader stuck-detection signal to cover.
- **sd:agent-durability:stateless-loop-durable-state**: Unknown results — what to do when a worker crashes mid-tool-call and the call's true outcome is unknown — is one of the six agent-durability techniques but isn't represented here; this overview shows the worker crashing cleanly between turns, not the harder case of a crash during a call in flight.
- **sd:transcript-checkpoint**: The concrete 'turn 37' is a good detail, but the diagram doesn't say what happens to a turn that was in progress but not yet checkpointed when the crash happened — is it re-run in full, or is partial work also recoverable? That gap is exactly where unknown-results (sd:unknown-results) becomes necessary.
- **sd:stateless-loop**: The reattachment mechanics aren't shown — how the new worker knows which environment to reattach to, and how it confirms the old worker is actually gone rather than still running. Without that check, two workers could both reattach to the same environment at once, which is exactly what worker-leases (sd:worker-leases) exists to prevent.
- **sd:env-snapshots**: Snapshotting every N turns means anything the environment did between the last snapshot and the crash is lost on restore; the diagram doesn't show this gap or how it's reconciled against the transcript, which (per sd:transcript-checkpoint) records every turn with no gap.
- **sd:worker-leases**: Fencing matters most when the stale write arrives after the current one, which could otherwise silently overwrite newer state; the diagram doesn't show this ordering, which is the actual scenario the mechanism protects against.
- **sd:unknown-results**: Reconciling requires the remote system to expose some way to check whether the action landed (a commit SHA, a message id, a charge id); the diagram assumes this is always possible, but many APIs don't expose an idempotency key or a lookup for an unacknowledged call, in which case this path isn't available.
- **sd:resumable-events**: The diagram doesn't say how long events are retained before they age out; a viewer that reconnects after the retention window has passed has no valid 'last id' to resume from, and there's no fallback edge for that case, such as falling back to a fresh snapshot.
